# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

An agentic application that automatically writes and publishes LinkedIn posts tailored to a domain the user selects (e.g., AI, fintech, HR). The pipeline: user picks a domain → agent gathers fresh content for that domain (news/RSS/search) → LLM drafts a post → post is published to LinkedIn via the official API, on a schedule, optionally after human review.

**Status:** OAuth connect, publish-to-profile, the news/topic content pipeline, explainer images, and daily scheduling with a review queue all work (first real post published 2026-07-19). Not yet built: a real database (state is still local-file stopgaps — cookie session, persisted token, history, schedule, queue).

## Commands

- `npm run dev` — dev server (Turbopack) at http://localhost:3000
- `npm run build` — production build; also the fastest full type-check
- `npm run lint` — ESLint

Requires `.env.local` (copy from `.env.example`): `LINKEDIN_CLIENT_ID`, `LINKEDIN_CLIENT_SECRET`, `LINKEDIN_REDIRECT_URI`, optionally `GOOGLE_GENERATIVE_AI_API_KEY` / `AI_MODEL` for draft generation, and `CRON_SECRET` to protect `/api/cron` (Vercel Cron sends it as a Bearer token; when unset, `/api/cron` is open in dev only). The redirect URI must also be registered in the LinkedIn app's Auth tab.

## Architecture

Next.js 16 App Router, TypeScript, Tailwind. No database yet.

**Auth flow:** `app/api/auth/linkedin` sets a `state` cookie and redirects to LinkedIn → `app/api/auth/linkedin/callback` verifies state, exchanges the code, fetches `/v2/userinfo`, stores `{accessToken, expiresAt, personId, name}` as JSON in the httpOnly `li_session` cookie (for interactive requests) AND persists the same object server-side via `saveAccount` (for the scheduler) → `lib/session.ts#getSession` reads the cookie everywhere interactive and returns `null` when expired (callers must treat that as "reconnect required"). Logout clears both and disables the schedule.

**Token store (`lib/account.ts`):** server-side persistence of the LinkedIn token at `data/account.json` (gitignored — it's a secret; local-file stopgap, single-user). The scheduler has no browser cookie, so it reads the token here: `getUsableAccount()` returns the account or `null` when missing/expired. Because the cookie was the only store before this landed, an existing connection must **reconnect once** to populate `account.json`.

**LinkedIn client (`lib/linkedin.ts`):** all LinkedIn HTTP calls live here — authorize URL, token exchange, userinfo, and `createPost` (versioned Posts API `POST /rest/posts`, `LinkedIn-Version` header from `LINKEDIN_VERSION`, defaulting to two months before the current date so it stays inside LinkedIn's 12-month active window). `commentary` text is escaped for LinkedIn's "little text" reserved characters before sending; keep that when touching post creation.

**Publishing:** `app/api/post` (session-gated, 3,000-char limit) validates then calls `publishPost` (`lib/publish.ts`), the shared helper that uploads the optional image, calls `createPost` (returns the post URN from the `x-restli-id` header), and records history. The scheduler and review-queue approval use the same `publishPost`, so all three publish paths behave identically.

**Scheduling (`lib/schedule.ts`, `lib/queue.ts`, `lib/run-scheduled.ts`):** the schedule config (`data/schedule.json`: `enabled`, `mode`, `domain`/`topic`, `notes`, `attachImage`, `autoPublish`, plus `lastRun*`/`lastError` status) drives a once-daily cycle. `runScheduledJob(force?)` is the core: it enforces the ~1/day cap via `lastRunDate` (UTC), checks `getUsableAccount` (records `lastError` for the UI instead of throwing on expiry), runs `generatePost`, optionally `generateExplainerImage` (a failure there is swallowed — image is optional), then either publishes (when `autoPublish`) or drops a `QueuedDraft` into the review queue (`data/queue.json`). It never throws — every outcome is recorded in the schedule status. `app/api/cron` (GET, Bearer `CRON_SECRET`) is the Vercel Cron entry (see `vercel.json`, daily `0 13 * * *`); `app/api/schedule/run` (session-gated, POST) is the dashboard "Run now" and passes `force` to bypass the daily cap. `app/api/schedule` (GET/POST) reads/updates config; `app/api/queue` (GET list, POST `{id, action: approve|discard}`) drives the review queue — approve publishes via `publishPost`, then removes the draft. **Human-in-the-loop is the default** (`autoPublish` false → everything queues); auto-publish is opt-in per the hard constraints.

**Content pipeline (`lib/pipeline.ts`):** `generatePost({mode, domain?|topic?, notes?})` runs a LangGraph agent graph (`@langchain/langgraph` for orchestration/state only — every model call goes through `callAgent`, AI SDK `generateText` + `Output.object` with `@ai-sdk/google`, model from `AI_MODEL`, default `gemini-2.5-flash`). Two modes branch at the entry and converge on a shared tail. **News mode:** **fetchNews** (Google News search RSS via `lib/news.ts`, no API key, `when:7d` window, deduped against post history) → **curator** (picks the most post-worthy item + the technical angle to explain). **Topic mode** (explain a concept, no news): **gatherReferences** (Wikipedia search + plain-text extract via `lib/wikipedia.ts`, keyless; throws if no usable article or the topic's wiki URL is already in post history) → **planner** (teaching angle + 2–3 point outline). Shared tail: **researcher** (news mode fetches the real article text via `lib/article.ts` — decodes/resolves Google News redirect links, falls back to headline+snippet when unreachable; topic mode reuses the Wikipedia extract — then extracts source facts, the only ground truth downstream) → **writer** (mode-specific structure, grounded strictly in those facts) → **factChecker** (verifies the draft against the facts; on fail, loops back to writer with a critique — max 3 drafts, then throws). Validation strips markdown (LinkedIn renders it literally) and enforces the 3,000-char limit; empty feeds, missing references, oversized drafts, and repeated fact-check failures throw — surfaced to the UI, never silently patched. `app/api/generate` wraps this and returns `{text, source}`; it returns 501 when `GOOGLE_GENERATIVE_AI_API_KEY` is unset so the UI degrades gracefully. Note the fact-checker verifies faithfulness to the fetched source, not real-world truth.

**Explainer images (`lib/explainer.ts` + `lib/render.ts`):** hand-drawn-notebook-style PNGs (1080×1350) that visually explain the post. Deliberately NOT AI image generation — text accuracy matters, so Gemini produces a structured spec which `renderExplainerHtml` renders as HTML/CSS (Caveat + Kalam Google Fonts, curated SVG icon set in `ICON_SVGS`) and Playwright screenshots via the system Chrome (`channel: "chrome"`, `playwright-core` — kept in `serverExternalPackages` in next.config.ts). The layout adapts to the post: a first model call picks one of seven layouts (`LAYOUTS`), then a second generates that layout's spec (a discriminated union on `layout`, all strings with word limits sized to the fixed page) — **process** (numbered steps + SVG flowchart with a No-loop, for how-something-works posts), **comparison** (two-column table + verdict, for X-vs-Y posts), **keypoints** (key facts + standout stat + why-it-matters, for news/announcement posts), **timeline** (dated milestones down a vertical line, for evolution/history posts), **dosdonts** (green Do / red Don't columns + golden rule, for best-practice posts), **mythsfacts** (struck-through myth / fact pairs + bottom line, for debunking posts), **mindmap** (central bubble with left/right SVG branch boxes, for landscape-overview posts). Array sizes carry only a `.min(1)` non-empty guarantee — the upper cap is enforced by post-call slicing, not zod bounds, because Gemini overshoots `maxItems` and can't reliably hit a high `minItems` on thin posts (both throw `NoObjectGeneratedError`); a sparse image beats a hard failure. Each layout's render helper lives in `lib/render.ts` (`processHtml`/`comparisonHtml`/… dispatched by `middleHtml`).

The whole image step is a second LangGraph loop in `lib/image-pipeline.ts` (`generateExplainerImage(domain, postText, layout?)`), separate from the post pipeline: **pick** (layout, skipped when the caller pins one) → **compose** (`buildSpec`, regenerates with the reviewer's critique on a revision pass) → **render** (`renderExplainerPng`, which also measures `overflowPx` — content clipped past the fixed 1350px height) → **review** (multimodal Gemini scores the rendered PNG 1-10 for legibility/layout/faithfulness) → conditional edge back to **compose** on fail, else END. A render passes when there's no overflow (deterministic, the reliable signal) and the vision score ≥ `PASS_SCORE` (6, a noisy backstop); overflow is a hard fail regardless of score. Max 3 attempts; unlike the post pipeline it does **not** throw on exhaustion — the image is optional decoration, so it returns the best-scoring attempt with its `score` (surfaced in the composer), deleting the losing renders as it goes. The route returns `{file, url, title, score}`. Vision review uses a `file` content part (`mediaType: "image/png"`), not the deprecated `image` part. Preview quickly with `npx tsx scripts/render-sample.ts` → `data/images/`. `app/api/image` (POST) generates from `{domain, postText}`; `app/api/image/[file]` (GET) serves previews. On publish, `app/api/post` uploads the PNG through LinkedIn's Images API (`uploadImage` in `lib/linkedin.ts`: initializeUpload → PUT binary → poll until AVAILABLE) and attaches the URN as `content.media`.

**Durable storage (`lib/kv.ts`):** the small single-user JSON stores — `account`, `schedule`, `queue`, `history` — go through `kvGet`/`kvSet`/`kvDel`, backed by Upstash Redis when `KV_REST_API_URL`/`KV_REST_API_TOKEN` (or the `UPSTASH_REDIS_REST_*` pair) are set (production on Vercel, via the Marketplace "Upstash for Redis" integration), and by a local JSON file per key under `data/` otherwise (so `npm run dev` needs no Redis). Each store module (`lib/account.ts`, `lib/schedule.ts`, `lib/queue.ts`, `lib/history.ts`) keeps its original interface — only the persistence swapped from `fs` to `kv`.

**Post history (`lib/history.ts`):** durable list under the `history` key (see `lib/kv.ts`). `app/api/post` records `{domain, postUrn, sourceTitle, sourceLink}` after each successful publish; `postedLinks()` feeds the pipeline's dedupe.

**UI:** `app/page.tsx` (server component) branches on session; `components/post-composer.tsx` (client) drives on-demand generate/publish; `components/scheduler.tsx` (client) is the schedule settings panel + status + "Run now" + review queue, all against the schedule/queue routes.

**Serverless caveat:** JSON state (account/schedule/queue/history) is now durable via Upstash Redis (`lib/kv.ts`), and image rendering uses `@sparticuz/chromium` on Vercel (`launchBrowser` in `lib/render.ts` branches on `process.env.VERCEL`), so the app runs on Vercel serverless. Still ephemeral: **rendered PNGs** are written to `/tmp/data/images` (fine — they're uploaded to LinkedIn on publish), so a review-queue draft's image may be gone by the time it's approved on a later/cold instance; durable draft images would need Vercel Blob (not yet built).

## Hard Constraints (do not violate)

- **Official API only.** Posting to LinkedIn must go through the LinkedIn Posts API. Never implement browser automation or scraping to post — it violates LinkedIn's Terms of Service and gets user accounts restricted.
- **Token lifecycle.** LinkedIn access tokens last ~60 days and do not auto-refresh for most apps. Expiry must be detected and surfaced to the user for re-authorization — never fail silently.
- **Posting frequency.** Cap automated posts (target ~1/day per user). Deduplicate against post history so the same article/topic is never posted twice.
- **Human-in-the-loop by default.** New posts should land in a review queue unless the user has explicitly enabled fully automatic publishing.
- **Failure behavior.** If the token is expired, the API is down, or the LLM output fails validation, notify the user — never publish low-quality fallback content and never drop errors silently.
